Data Platform Reliability Agent

The problem
A pipeline error rarely explains the whole incident. Engineers need the run history, expected data structure and operating guidance together.
The approach
Combines synthetic incident records, data contracts and retrieved runbooks into an evidence-backed diagnosis and proposed next steps.
What it demonstrates
A traceable investigation with a clear approval boundary. The demo recommends actions but cannot execute repairs.
Read the case studyView source code
Technical details and scope

FastAPI, Pydantic, tenant-scoped SQL and local Qdrant retrieval. The optional OpenAI planner is separate from the deterministic offline evaluation.

Independent synthetic implementation. Its regression checks do not establish production readiness or the quality of the optional LLM planner.

Synthetic Data & Print Recommendations

The problem
A small labelled dataset can miss important variations. Generating more rows can repeat the same gaps instead of improving coverage.
The approach
Measures coverage, generates controlled document variations and compares recommendation behaviour at different dataset sizes using a separate synthetic holdout.
What it demonstrates
A way to inspect coverage and saturation, with structured recommendations, supporting evidence and a human-review flag.
Read the case studyView source code
Technical details and scope

Python feature engineering, controlled 1×/10×/100× generation, duplicate and diversity checks, an API and holdout records with disjoint IDs.

All document profiles and labels are synthetic. The holdout uses the same synthetic policy world; these results do not establish real-world print quality.

Constraint-Aware Coding Agent Evaluation

The problem
Code can return the expected answer while still changing inputs or breaking other operating constraints.
The approach
Runs ordinary functional tests and six focused behaviour checks separately, using authored reference and comparison implementations.
What it demonstrates
Both examples pass the ordinary tests. The additional checks expose behaviour that those tests missed.
Read the case studyView source code
Technical details and scope

Python runtime probes check iterable use, object identity, input mutation, time snapshots, injected dependencies and stable ordering. Results are reproducible.

A small, fully synthetic evaluation lab. The candidates were authored to exercise the checks; the results are not scores for a commercial model or production coding agent.

PII Masking Lab

The problem
Customer query case logs can contain contact or payment information alongside useful technical details. Masking must preserve the issue being investigated.
The approach
Tests sensitive-data detection, validates candidate text spans and replaces identified values while keeping the surrounding customer issue readable.
What it demonstrates
Why a masking workflow needs checks for missed information and unnecessary masking, alongside checks that the replacement itself is correct.
Read the case studyDownload notebook & code
Technical details and scope

Python notebook with a rules-based baseline, candidate validation, overlap checks, right-to-left span replacement and automated tests. Optional LLM detection is a separate path.

The linked public learning lab uses synthetic customer query case logs. It is separate from workplace implementations and is not a production privacy filter.

A few questions
before we start.

A focused engagement should fit your team, your systems and the decision you need to make.

Do we need to replace our existing systems?

The starting point is the tools and data your team already uses. Discovery identifies whether exports, APIs or a small integration can solve the problem. Any additional software or platform changes are agreed as part of the scope.

What if our data is still in spreadsheets or incomplete?

A focused data review can be the first engagement. We agree the essential fields, identify gaps and build a useful baseline before deciding whether an AI pilot is appropriate.

How do we decide whether a pilot is working?

Agree the baseline and acceptance criteria before the build. Depending on the workflow, these can include time spent, error rates, data freshness, answer quality or planning accuracy. Review the result alongside operating costs and the effort needed to maintain it.

What will our team receive?

The agreed working solution, documentation, tests or evaluation results and a handover. Access, ownership, review responsibilities and any ongoing support are defined in the engagement scope.

What would you like
to work better?

Tell me where work slows down, what your team uses today and what a better result would mean. We can use that to define a sensible first step.
